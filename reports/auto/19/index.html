技术委员会 19 项场景　技术可检性分析

本版不考虑需求范围裁剪，只回答：在「源码检测 + 仅鸿蒙 SDK 开源代码仓作为输入」下，技术上能否检出。每条直接给出能检出什么、检不出什么。

方法论
源码静态检测
输入范围
63 个开源代码仓
判定结果
支持 3 · 部分支持 13 · 不支持 3
结论
16 条至少有一部分可检

判 定 依 据

每条场景的可检性只取决于两个问题：

问题不满足时的后果
一、变更在不在我们能看到的代码里？变更发生在扫描范围外的仓、或根本不在任何开源仓（伙伴应用、设备固件、第三方闭源组件）→ 看不见，无从判定
二、看见了，能不能判断它是不是破坏？差异可见但缺少判据——机型能力数据不存在、性能数值无承诺、语义变化无任何锚点 → 看得见，判不了
一条贯穿全表的规律：契约层全覆盖，实现层看仓

契约层：interface_sdk-js 下 552 个 .d.ts 涵盖全部 @ohos.* API 声明与标注（@throws 44,757 处、@returns 8,967、@permission 5,391）。任何能力域的 API 契约变化都能检出，与它的实现仓在不在范围无关。

实现层：只覆盖 63 个仓。third_party_*（9 个）、llvm-project、window_window_manager、multimedia_av_codec 在范围内；arkweb、ai_intelligentvoice、audio_framework、resourceschedule、ability_runtime 不在。

所以多数「部分支持」的形态是同一个：API 契约能检，内部实现看仓在不在。

范围的判定依据：以索引构建产物 compat_index_sources_manifest.json 的 source_repos 为准，共 63 个仓、53,922 个源文件被实际读取。磁盘上另有 cangjie_test 目录未纳入索引。
另需注意：repo_baseline.csv 只记录 46 个仓，它不是扫描范围，仅记录需跟踪 git 版本的仓子集，不可用作范围依据。
63 个仓中有 7 个 *_cangjie_wrapper 仓被索引文件数为 0（空仓或未拉取内容），故有效仓约 56 个。

说明：这是输入不具备，扩大扫描范围也无法解决，除非伙伴代码开源并纳入。属方法论硬边界。

需注意：完备性检查技术可行，但它回答的是「新增设计是否合规」，与本需求的「变更是否破坏已有契约」是两个命题。技术上可合并实现，产品上建议分开定义验收口径。

14是否性能优化后影响兼容性部分支持性能数值除外
能检出

能检出
性能特征的文档承诺变化　SDK 中有 53 处性能特征描述，如 Creating a module context ... can be time-consuming、Use the asynchronous version ... in non-blocking scenarios。实现由非阻塞改阻塞而描述未同步＝契约漂移　覆盖度低：53 处对 552 个声明文件，只能作补充锚点
能检出
静态可见的性能模式变化　引入新的 IPC 调用、循环嵌套层级变化、资源申请模式改变　只能作风险提示：「复杂度上升多少算破坏」无静态判据
检不出
性能绝对数值　耗时由 10ms 变 50ms、内存占用上升 → 需真机基准。文档说「time-consuming」不等于承诺了具体耗时
需明确一个前提：性能劣化确实构成破坏性变更（它迫使开发者改代码或配置）。检不出的只是数值判定，不是「性能与兼容性无关」。
15是否安全策略变更影响兼容性部分支持系统策略的仓不在范围
能检出

能检出

检不出
系统沙箱规则、证书校验策略　相关实现仓不在扫描范围
建议评委细化：「安全策略」覆盖面很广。凡最终落到 API 前置条件或异常契约的，判据都明确；落到系统策略的，取决于仓是否纳入。
16是否在升级后影响应用的流畅性和稳定性不支持
检不出
流畅性与稳定性表现　帧率下降、崩溃率上升 → 运行时观测量，源码静态分析无从判断
相邻可做
可静态识别的诱因（异常处理分支被移除、资源释放路径改变）本身可检出，但检出的是变更，不是稳定性影响——从变更到稳定性结论的因果链无法静态建立
说明：与第 14 条数值判定同源。这类问题需由性能与稳定性测试、现网监控回答；检测能提供变更清单作为归因线索。
17是否在工具链升级第三方组件后验证兼容性部分支持未纳入仓的组件除外
能检出
已纳入范围的第三方组件　llvm-project 与 9 个 third_party_* 仓（brotli／cares／curl／iptables／libwebsockets／lwip／mbedtls／nghttp2／wpa_supplicant）在扫描范围内，升级带来的源码差异完全可见　成本高：判定「组件内部变化是否影响 SDK 对外契约」需借助消费者关系索引追踪调用链
检不出
未纳入范围的组件　以预编译库或 submodule 指针形式引入的，仓内仅体现为版本号变化
此条为修正项：初版判为不支持，理由是「第三方变更不在输入范围」。该判断不成立——第三方组件大量以 vendor 形式在仓内，变更完全可见。实际是技术可行、成本高。
18是否在升级 web 引擎后验证兼容性部分支持引擎内部行为除外
能检出
ArkWeb 对外 API 契约　@ohos.web.webview 的参数、@throws、@permission 变动 → 契约层在 interface_sdk-js 内
检不出
Web 引擎内部实现　内核升级导致的渲染差异、JS 引擎行为变化、CSS 支持度变化 → arkweb 仓不在扫描范围，且这类行为需运行时验证
准确表述：应说「支持 ArkWeb 对外 API 契约变化的检测」，而非「支持 web 引擎升级的兼容性检测」。引擎行为一致性需由 Web 兼容性测试套件回答——即使纳入该仓也难以静态判定渲染差异。
19语音唤醒功能与第三方应用播放逻辑是否冲突部分支持冲突判定本身除外
能检出
语音唤醒 API 契约　@ohos.ai.intelligentVoice 的契约变化——但这回答不了「会不会与别人冲突」
检不出
语音唤醒与音频焦点实现　ai_intelligentvoice、audio_framework 均不在扫描范围
检不出
第三方应用播放逻辑　不在任何开源仓，与第 09 条同因
说明：即使纳入音频框架仓，冲突判定仍不可行——它需要第三方应用的实现与运行时焦点竞争模型，前者输入不具备，后者非静态可判。

汇 总

判定数量条目共同特征
支持305、06、07变更完整体现在契约层与可见的实现层，判据明确
部分支持1301、02、03、04、08、10、11、12、14、15、17、18、19能力域横跨多层：API 契约能检，内部实现看仓在不在，运行时表现检不出。评审时须按「能检什么／检不出什么」两栏表述
不支持309、13、16输入不具备、命题错配、纯运行时表现
核心结论

19 条中只有 3 条完全检不出——09 伙伴冲突、13 发布测试、16 流畅性稳定性。其余 16 条都至少有一部分技术可行。

这与「本期能否交付」是两个问题。初版报告中判为不支持的 6 条，本版有 3 条修正：17（第三方组件在仓内可分析）、18 与 19 的契约层部分（在 interface_sdk-js 内可检）。另修正 02 的返回值取值含义——原判检不出，复查后有文档／消费方／基线三层锚点可判。

检不出的三类原因，只有一类无法解决

一、代码拿不到（09、19 的冲突判定）——伙伴与第三方应用代码不开源，任何工程手段都解决不了。

二、代码里看不出来（02 无锚点语义、04 机型级、14／16 数值判定）——差异要么不存在，要么存在但无判据。需引入运行时数据或外部数据源，不属静态检测范畴。

三、仓不在扫描范围（03、08、15、18 的实现层）——这一类可解决：纳入对应代码仓即可见。是投入问题，不是技术极限。

评审时区分这三类，比笼统说「不支持」更有信息量——「我们做不到」和「这需要扩大扫描范围」完全是两回事。

「部分支持」占 13 条，都是同一个形态：接口层面的变化能查出，系统内部策略与运行时表现查不出。汇报时若只说「支持」，听众会以为整个能力域都覆盖了。

三条「不支持」的原因不同：09 是代码拿不到，13 是问的不是代码的事，16 是要靠真机数据。只有 09 属于无论怎么投入都解决不了的。
