第 1 页

「多设备同一接口」场景的处理结论

设备类型级已有官方对照表，纳入支持；产品机型级无数据源，明确不支持并写入规格

配图　p1-multi-device-scope.png　（1200 × 700，2 倍图 2400 × 1400）

讲稿一：先拆场景，判据分两层且粒度不同

评审提出的「多设备同一接口」，按粒度可以拆成两层。这一步必须先讲清楚，否则容易被理解成整个场景都做不了：

  • 设备类型级（手机 / 平板 / 穿戴 / TV / 2in1 / 轻穿戴）：SDK 中有官方对照表 interface_sdk-js/api/device-define/*.json，六类设备各自枚举支持的最小系统能力集（每类 185–233 条 SysCap）。该表已随源码镜像并已入索引。这一层本期支持。
  • 产品机型级（同为手机的 A 机型与 B 机型）：官方对照表止于设备类型粒度，未细化到厂商具体产品机型。同类型内各机型的实际能力集由厂商 ROM 决定，不公开发布。这一层本期不支持。

评审举的 NFC 例子，按严格读法（同为手机的两个机型）落在第二层。若实际指的是「手机有、穿戴没有」这类跨设备类型差异，则落在第一层，我们现在就能检。

讲稿二：不支持产品机型级的三条理由

  1. 官方数据止于设备类型粒度。SDK 提供的是「设备类型 → 能力集」映射，没有「产品机型 → 能力集」这一层。这是数据本身的粒度上限，不是检索没做到。
  2. 机型级能力不随 PR 变更。它由厂商 ROM 在出厂时确定，与代码仓的任何提交无关。而兼容性结论的一等证据边界是当前 PR 的真实改动，因此无论 PR 怎么变，都取不到这个判据。
  3. 无可替代的取证路径。在缺数据的前提下强判，只能退化为模型推测。系统现行护栏要求证据不足时给保守结论，强判必然产生误报，直接冲击 SR2 的准确率目标。

需求规格声明（可直接粘贴进 SR 需求描述）

【设备维度支持范围声明】

本需求的 API 兼容性检测基于 PR 代码变更进行静态分析，检测依据限定于代码仓内容与 PR diff 范围。

（一）支持范围。设备相关的检测限于以下三项声明侧契约：接口 SystemCapability 系统能力标注的变更；应用配置 module.json5 中 deviceTypes 设备类型声明的收缩；条件编译导致的平台可见性收缩。判定粒度为设备类型级（手机、平板、穿戴、轻穿戴、TV、2in1），依据为 SDK 中随版本发布的设备类型能力对照表。

（二）不支持范围。产品机型级硬件能力差异检测，即同一设备类型内不同厂商产品机型之间，因硬件配置差异（如 NFC、UWB 等）导致的接口可用性不同。原因是官方能力对照表止于设备类型粒度，机型级能力集由厂商 ROM 决定且不公开发布，亦不随 PR 变更，检测系统无取证途径。

（三）后续演进。若能够提供产品机型级的 SystemCapability 实例化数据，机型级能力差异检测可作为独立需求另行评估立项。

检测能力全景：四类场景与支持规格

以白名单与黑名单方式，明确每类场景的检测逻辑、证据支撑与建设状态

配图　p2-detection-design.png　（1760 × 900，2 倍图 3520 × 1800）

讲稿一：分类依据是「调用方如何依赖契约」

兼容性破坏的本质是「调用方依赖的契约变了」。因此场景应按依赖方式划分，而不是按语言或组件划分。据此得到四类：

  • A　直接符号依赖：通过显式函数调用或链接消费，契约载体是符号本身。已建成
  • B　非直接符号依赖：通过消息、协议、产物消费，代码里没有对被改方的符号引用。这正是评审提到的「通过消息消费而非显式函数调用」。部分待建
  • C　部署与可见性：契约是「在哪里可用」而非「怎么调用」。部分待建
  • D　访问前置与版本：契约是「调用需满足什么条件」——权限、API 版本、废弃状态、失败语义。已建成

关于「除这两类外是否还有其他场景」：有，而且是两类。C 类（第 1 页讨论的多设备同一接口即属此类）与 D 类都不属于直接／非直接符号依赖——D 类尤其容易被忽略：权限收紧既不是签名变化，也不是消息消费，而是调用前置条件变了，旧调用方代码一行不改也会失败。

讲稿三：B 类新建能力的三层检测逻辑

「格式不变、语义变化」是评审关注的核心难点。做法是不去理解语义，而是盯住可观测的语义锚点：

  1. L1 结构锚点（自动判定，误报低）：抽取消息契约卡片——主题名／事件名常量、payload 字段名与类型、必填可选；建立发布方与订阅方的配对关系。主题改名、字段删除、类型变更、必填字段新增，直接判破坏。
  2. L2 语义锚点（触发深查）：取值域变化（状态码含义改变）、单位量纲变化（ms→s、B→KB）、触发时序与次数变化（每次触发改为节流触发）、触发条件收窄放宽、错误分支变化（静默失败改为发送错误事件）。这些锚点全部落在 diff 内的常量与条件上，可复用现有事件分类机制触发。
  3. L3 消费者核验（定级而非直判）：命中锚点后，用订阅关系找出全部消费方，判断是否已在本 PR 组合中同步适配。有残留订阅方则判不兼容；无残留则降为高风险并输出补证清单。

需求规格声明（可直接粘贴进 SR 需求描述）

【检测能力边界声明】

（一）非直接符号依赖场景的承诺边界。本需求支持检出锚点可观测的契约与语义变化，包括消息主题与事件名、payload 字段与类型、字段顺序、取值域、单位量纲、触发时序与条件、错误分支等可在代码变更中观测到的锚点。对于主题名、数据格式、字段定义、触发时序、触发条件均未改变，仅业务语义发生变化，且无消费方适配证据的纯语义漂移，本需求不支持检出。

（二）运行时性能。本需求不支持对运行时性能绝对值（耗时、内存、功耗的具体数值）的检测与判定，该类判定需真机基准环境与对照测试支撑。当代码变更中出现算法复杂度、资源申请模式、同步异步模型等明显变化时，作为风险提示输出，不作为兼容性结论的独立判定依据。

第 3 页

输入规格与流程联动机制

检测输入限定为 PR 链接一类；设计态不作为支持场景，联动通过规则前移实现

配图　p3-input-spec-linkage.png　（1300 × 760，2 倍图 2600 × 1520）

讲稿一：支持的输入只有一类

输入形态说明是否支持
单 PR 链接最小检测单元支持
多 PR 组合跨仓联动改动，按组合 head 判断调用方是否已同步适配支持
关联 PR 扩展平台按既定规则试算关联 PR 后并入同一分析集支持
API 设计稿 / 接口清单 / 自然语言描述设计态输入，无对应实现不支持

三种支持形态输入实体相同（都是 PR 链接），区别只在分析集的组装方式。触发方式有两种：接入代码仓门禁自动触发，以及在平台上人工提交——两者走同一套检测逻辑。

讲稿二：为什么只支持 PR 链接

PR 链接同时满足三个「可约束」条件，这是它能作为检测输入的根本原因：

  1. 有确定的 diff 范围　→　结论有明确的证据边界，可被出站校验强制要求回连到真实改动，杜绝凭空推断。
  2. 有已落地的实现　→　可反查真实源码、真实调用方、真实文档，而不是依赖对描述的理解。
  3. 有稳定的唯一标识　→　可复盘、可重测、可纳入准确率统计口径。重测一致性本身也因此成为可度量的质量指标（见第 4 页的后冒烟数据）。

讲稿三：为什么设计态不作为支持场景

设计稿与自然语言描述一条都不满足上述三个条件：

  • 没有 diff，就没有证据边界。系统现有的出站校验要求不兼容结论的证据路径必须命中当前 PR 的真实改动，设计态输入下这套校验完全无从生效，结论质量失去唯一的兜底机制。
  • 同一份描述可对应多种实现。同样一句「新增一个查询接口」，不同实现的兼容性结论可能完全相反。结论既不可复核，也无法重测验证。
  • 无法纳入准确率统计。准确率按 PR 维度聚合，设计态输入没有 PR 主体，混入只会稀释 SR2 的可度量性。

讲稿四：那么「在设计阶段起效果」怎么实现

评审这条意见的目标是对的，应当采纳；分歧只在实现路径。正确做法是规则前移，而不是扩大输入类型：

  • 规则集对外发布，作为设计自查清单。门禁中已验证生效的规则集与历史判例，整理为开发者在设计阶段可直接查阅的清单。这些规则经过实测校准，设计阶段拿到的是可信结论，而不是对无实现描述的推测。
  • 申请流程支持前置登记。确定要做破坏性变更时，可在编码前先登记申请单，走审批流程，而不必等到门禁拦截。
  • 检测入口保持唯一。规则可以前移，但检测结论必须以真实实现为准。这样既满足「设计阶段起效果」，又不引入无法约束、无法度量的输入类型。

【输入规格声明】

（一）支持的检测输入。GitCode PR 链接，包括单个 PR、多个 PR 组成的跨仓联动组合，以及平台按既定规则试算后并入的关联 PR。支持接入代码仓门禁自动触发，同时保留平台人工提交入口；两种触发方式的输入形态一致，均为 PR 链接，走同一套检测逻辑。

三项口径说明（必须主动先讲，不要等被问）

6.0%：后冒烟候选按设计只选取「首次判定为兼容且已合入」的 PR，因此不一致方向必然是「兼容 → 不兼容」，这是筛选口径决定的，不是发现了系统性偏差。正确解读是：在已合入且首次判兼容的样本上，漏报率的一个下界估计。
0.73% 及其结果：27 条人工复核中，21 条为「不兼容 → 兼容」的修正，5 条维持原判，1 条为「兼容 → 不兼容」。人工只在怀疑结论有误时才介入，故该样本的错判密度远高于总体，不可外推为准确率。它能证明的是：不兼容侧误报是当前主要失分方向——这也正是层三看护集优先建设的原因。
5.8%：待办目录共 245 项，其中 159 项为含试点仓的历史待办，按既定规则已剔除出统计且未执行优化（目录留空壳），活跃待办为 86 条，其中已归档 5 条。

讲稿三：四层闭环设计

  1. 层一　采集——现有触发器集中在复盘侧，88% 落在「结论不一致」一类。新增四类信号源并入同一队列：后冒烟不一致（41 条现成数据）、人工修正（27 条最高质量标注）、门禁评论区的开发者误报反馈按钮、影子模型分歧样本，使信号源由 1 类扩至 5 类。
  2. 层二　标注——现有待办为 Markdown 叙述式模板，已含命中问题、期望结论、参考日志路径，但字段未结构化落库、无法聚合查询，且缺少「错判类型」分类维度。需强制落库三个结构化字段：期望结论、关键证据路径、错判类型（漏报／误报／证据不足／规则冲突）。错判类型是按根因合并待办的唯一依据。
  3. 层三　看护（最高优先级）——用「已归档待办＋人工修正＋后冒烟不一致」三类真实样本建立回归看护集，每条含输入 PR、期望结论、关键证据、易错点。配套上线门槛：任何规则、索引、技能变更，必须先跑看护集，通过率不下降才允许同步生效。
  4. 层四　度量——四项指标常态化：准确率、消化率、复发率、看护集通过率。并规定每次优化必须记录 before / after 的看护集通过率，无提升的优化不计为完成。同时按错判类型聚类合并同类待办，解决消化率断裂。

讲稿四：实现约束（体现方案的严谨性）

  • 看护集必须与分析期检索路径物理隔离。系统现有护栏明确禁止历史结论作为当次判定的证据或缓存。看护集取材于历史结论，若被分析期检索命中，会把「质量看护」变成「结论缓存」，反而破坏检测独立性。
  • 待办限流须留例外通道。复盘是待办队列目前唯一的填充源，若因超阈值全量暂停，队列会彻底静默，期间发生的结论稳定性回退将无从发现。
  • 待办聚类的前提需先验证。错判类型字段尚未落地，「同类占比高」目前是假设。建议先抽样 20–30 条实测同类占比，再决定聚类合并的投入。
